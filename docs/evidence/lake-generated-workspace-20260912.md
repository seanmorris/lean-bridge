## Source staging and resolution

`prepareGeneratedLakeWorkspace` takes an opaque complete source capture, selected root modules, completed generator prerequisites, and the prerequisite digest retained by the build handoff. It reads recipes from a verified copy of the original capture and validates every selection and output receipt before copying files.

The private workspace contains the captured sources and the exact generated Lean/C/header outputs. The original snapshot document and its digest remain unchanged. A separate [workspace receipt](../../schema/lake-generated-workspace.schema.json) binds each output path, size, hash, mode, generator key and generator receipt digest. Generated outputs are limited to 16,384 files and 256 MiB across the workspace, in addition to each generator's existing limits.

Verification rejects changed bytes, executable modes, symlinks, missing files, extra files and unexpected directories. Reads are bounded by the authorized file size, including during concurrent growth. Snapshot verification still rejects a generated workspace as an original source capture. Staging never adds generated bytes to that capture's authority.

`resolveGeneratedLakeWorkspace` creates its own verified workspace and re-runs the selected Lean installation's Lake resolver. Lake parses the actual generated import headers, discovers their transitive source imports, and checks module ownership and dependency order. The final prerequisite set must equal the set selected before generation. Imports that introduce another generator fail instead of starting an implicit second generation round.

Declared `input_file` C sources may be absent during planning only when an exact recipe output names them. A selected library must select that output's producer. Native inputs on a missing generated module participate in this check too. Unselected libraries do not force their generated outputs to exist. Neither resolution pass invokes custom target bodies.

The separate [resolution receipt](../../schema/lake-generated-resolution.schema.json) binds the original snapshot, prerequisite receipt, workspace receipt, resolver, Lean compiler and Lake library. Every source record identifies its captured or generated origin. Re-resolution uses the same compiler/library identities as generation. Verification rechecks the full compiler library inventory, staged inputs, request and module copies. The ordinary captured-source receipt validator cannot accept this new receipt format.

The returned resolver owns its copied outputs. Disposing the original prerequisite result does not invalidate those copies. Repeated disposal succeeds; failure and cancellation remove owned staging. Lean configuration evaluation and compiler initializers retain normal trusted-Lean behavior. Private staging is not an OS sandbox.

## Internal API sequence

```js
const prerequisites = await prepareLakeGeneratorPrerequisites({
  snapshot, modules, leanPrefix
});
let resolved;
try {
  const expectedPrerequisitesSha256 = prerequisites.sha256;
  resolved = await resolveGeneratedLakeWorkspace({
    snapshot, modules, leanPrefix, prerequisites,
    expectedPrerequisitesSha256
  });
  await resolved.verify();
  // The next integration consumes resolved.sourceRoot, workspaceRoot and receipts.
} finally {
  await resolved?.dispose();
  await prerequisites.dispose();
}
```

For detached validation, retain the expected receipt digests outside the received documents. `validateGeneratedLakeWorkspace` and `validateGeneratedLakeResolution` check metadata against those identities and the independently captured recipe catalog. These validators do not execute Lake or inspect filesystem bytes.

## Remaining integration

Normal CLI builds still reject nonempty generator configuration. This milestone does not publish generated application packages. Native and WASM compilation, linking, bundle inventories and release receipts must next consume the separate output identities. Relocated offline installed npm/CPAN tests must exercise public APIs whose results depend on generated values before enabling that CLI path. Generated public entry-module discovery also needs explicit planner support.

VO1239 remains in progress. VO1238 owns reviewed foreign implementation contracts; VO1107/1108 own authoritative export extraction and stale-interface cutover. This milestone does not promote consumer type support.
